# Phase 4 · Intelligent calibration

**Decision.** One authenticated owner can collect, inspect, activate and restore a calibration for the single provisioned ESP32. A passing calibration changes only its sensor's permitted parameters. A failed or aborted run leaves its active version intact. Numerical agreement and lifecycle behavior have been tested in software. Physical calibration remains experimental.

## Session lifecycle and Phase 5 API

All owner routes retain Firebase ID-token authentication and the Phase 3 mutation Idempotency-Key contract. The workflow uses the existing collections, routes and RTDB paths. Additional session and version metadata lives inside the existing documents. No change to firmware, acquisition cadence, storage layout, security rules or retention is required.

| Action | Request | Response or effect |
|---|---|---|
| Start | POST /api/calibrate/start with sensor equal to occupancy, mq135 or sharp and optional boolean conditions_confirmed | Returns session UUID, source version and warmup status. Only one session can be open. A duplicate key returns the original result. Another start conflicts. |
| Check progress | GET /api/calibrate/status, optionally with ?session=UUID | Without an ID, returns the active session, last completed session, or idle. Progress includes observations, stable-window count, distinct SCD count, elapsed/required window milliseconds, warnings, gate measurements, failure reason and candidate parameters. |
| Abort | POST /api/calibrate/abort with session | Marks the matching active session aborted and releases calibrating mode. Retry the same key on transport failure. |
| Export | GET /api/export/UUID | Streams the existing sensor-specific CSV header and columns in capture order for a single boot. Unknown fields are blank. PC/local/ISO timestamps are UTC estimates based on the ingest clock offset. Sensor uptime and sequence remain the capture references. Occupancy labels stay blank and training_eligible is zero. |
| Restore previous calibration | POST /api/model/rollback with model and version equal to the passing session's source | Atomically switches the pointer, invalidates the cached spec bundle and fences the old model state. Use a fresh mutation key for a new action. Check the version in the next live sample. |

**Consent and room conditions.** Send conditions_confirmed=true only after the operator confirms an empty room, a reference environment suitable for the selected sensor, and stable airflow without deliberate activity throughout collection. Start without confirmation remains compatible with the Phase 3 capture-only request; evaluation records a failed confirmation gate. A changed room condition calls for abort. Low CO₂ cannot establish that the room is empty. A fan-on sample invalidates the run. Fan decisions, reported actuator state and the ESP32 high/stale local overrides continue during calibration. Closing or opening a window can invalidate the experiment even when every numeric gate passes.

**Timing.** Warm-up starts at the first accepted post-start capture. When the sensor is ready, the backend begins a 60-second capture window. Evaluation runs in the final ingest transaction. Intermediate state is warmup or measuring; terminal state is passed, failed or aborted. Distinct fresh SCD samples supply environmental statistics, while every Sharp aggregate participates in filtering. Raw export includes warm-up and the terminal observation. The final session record includes stage, gate results, warning flags, sample counts and time range.

**Continuity.** The collection binds to its boot and source version. Firestore serializes progress with the ingest cursor. Duplicates do not advance the window. A reboot, proven gap, current-session replay, invalid pulse or lost freshness can fail the session. Without telemetry, the next status read or new ingest detects the timeout; no scheduler is assumed. An unfinished pre-Phase-4 collection lacks the new gate evidence and cannot activate a version. The owner can abort it or start again after the next ingest marks it failed.

## Versioning and recovery

- **Occupancy:** replace HISTORICAL_EMPTY_CO2_PPM only. Preserve the imported Ridge, scaling, clipping, rounding and domain metadata. Occupancy remains approximate after recalibration.
- **MQ135:** the owner approved the reconstructed fitter for activation in this phase. R0, T0 and RH0 are the eligible medians of Rs, T and RH. x0 is median ln(R0/Rs). Store the approved firmware coefficient signature with those anchors. The backend uses the active calibrated reference before the legacy NVS reference. Returning to v0 restores the firmware-supplied reference, subject to validation. Five betas, correction, robust center/scale, EWMA, votes and anomaly limit retain Phase 1 values. The historical fitter is still unknown.
- **Sharp:** replace baseline and spread; derive low = baseline − 3 spreads, elevated = baseline + 3 spreads, high = baseline + 4 spreads. These multipliers reproduce F31 to its recorded precision. The rolling median, persistence and acquisition remain the approved values.
- **Storage:** existing calibrations/{session} stores the durable run. Existing minute children store CSV values, validity flags and capture uptime. A passing session's UUID is also its version ID. Its version document records sensor, predecessor, device/boot identity, run and window time range, parameters, comparisons, provenance, limitations, counts, gate outcomes, owner confirmation and creation time. Raw data acquisition is single-device authenticated; the firmware supplies a boot ID, not a hardware serial number.
- The terminal result, immutable new version, active pointer and invalidation of prior runtime state commit together. Batches use a single spec snapshot; the next observation loads the selected version and resets temporal state. A failed Firestore transaction leaves the predecessor active. Retrying a committed batch after RTDB failure repairs the projection without creating another version. Prior versions remain addressable. A restore racing collection changes the source-version fence; collection cannot promote against a different active source.

## Four-hour experimental quota scenario

The owner supplied the verified plan limits listed below. These figures model four hours/day; the device has no operating timeout. At nominal cadence this means 14,400 observations, 2,880 uploads and 240 completed minute documents/day.

| Resource | Planning result |
|---|---|
| Firestore reads/writes/deletes | Baseline ≈2,880 coordinator reads and 3,120 writes/day before owners, retries and boot transitions. Limits are 50,000 reads, 20,000 writes and 20,000 deletes/day. No deletes are scheduled. |
| Calibration marginal operations | For B accepted batches during collection, add B session reads and B session writes. Add one calibration-minute write per distinct minute touched **per batch** (usually B, up to two per ordinary ten-record boundary batch). These raw-row writes and session reads already existed in the Phase 3 capture path. A pass adds one pointer read and two writes (new version and pointer). The next runtime reload reads four pointers and four versions. Start normally reads coordinator + operation key and writes session + coordinator + operation result; first-use model seeding is extra. A status poll reads coordinator + session, and detecting timeout writes both. Abort/rollback, retries and exports also consume quota. |
| Worked session | A roughly two-minute run spanning 25 uploads and two extra crossed-minute writes adds about 34 reads and 54 writes over baseline ingest, including activation/reload but excluding owner calls. Cold MQ warm-up can add roughly ten minutes of raw collection. Repeated calibration or frequent status polling must be budgeted separately. |
| Firestore storage | Phase 3 measured ≈104 MB/day at 24 hours, hence ≈17.3 MB/day at four hours. At 1 GiB, roughly 62 such days of history consume the budget before indexes. Synthetic completed-session JSON (session, minute documents and version) occupied about 85 KB occupancy, 38 KB warm-device MQ and 48 KB Sharp. Actual bytes vary with run length, failed sessions, indexes and encoding. All records remain retained. |
| Firestore outbound | Phase 3's 64,110-byte mean coordinator read × 2,880 × 30 ≈5.54 GB (5.16 GiB) of logical reads/month. Compare with 10 GiB outbound/month. Calibration reads include the evolving session document per batch; exports, retries and region placement affect billable transfer. |
| RTDB | A 14,274-byte projection × 2,880 × 30 ≈1.23 GB/month in logical full projections. Stored current projection is on the order of tens of KB against 1 GB storage. Transactions, browser listeners and reconnect downloads count toward 10 GB downloads/month; every poll is not necessarily a full download. |
| Vercel Hobby | ≈86,400 ingest invocations/30 days versus 1 million/month, plus owner routes. At this invocation count, four active CPU hours allow an average of about 167 ms active CPU/request before other work. 360 GB-hours corresponds to 15 GB-seconds/request. Production CPU, memory duration and Firebase billing were not measured. |

The four-hour scenario postpones the storage conflict; indefinite retention still exceeds 1 GiB. Owner decisions remain the total experiment duration and eventual retention/export policy. Options for separate approval include bounded experiment dates or an explicitly reviewed archival policy. No TTL, paid services, deletion or cadence change was introduced. ## Evidence and physical experiment checklist

From web/, `npm test` reported **3 test files and 28 tests passed**, including the 19 Phase 3 regressions and unchanged golden vectors. Tests use synthetic sensor values and mock transactional stores. They cover three successful sensors, failed gates, abort, auth, concurrent starts, invalid pulses, insufficient independent SCD samples, interrupted and duplicate uploads, reboot, rollback, state reset, cold restart, transaction failure and projection retry. The export test checks recorded values against the source header, estimated timestamps and CSV serialization. `npm run typecheck` exited 0. `NEXT_TELEMETRY_DISABLED=1 npm run build` compiled all seven routes. From the repository root, `python3 -m unittest discover -s training -v` reported **Ran 5 tests, OK**. Path and byte comparison against phase-3 verified all 65 input files.

1. Complete the ESP32 target build and supervised wiring, timing and fan-safety tests. Verify real authentication, Firebase transactions, rules, CSV downloads and replay in an isolated authorized environment.
2. Identify the sensor/board, room, prior version and reference conditions. Log empty-room verification, airflow, doors/windows, fan state and any disturbances. Wait for MQ warm-up. Abort on changes.
3. Collect repeated independent runs across days. Compare full-window vs short-window Sharp spread, pulse rejection, calibrated alert frequency, climate drift and repeatability of MQ anchors. Include actual interruption and rollback trials.
4. Record the active version before/after, inspect warnings and raw exports. Independently label occupancy before making any headcount performance claim. Validate physical suitability before revising the provisional gates.

**Phase 5 readiness:** The owner-facing session API, status reasons, progress, warnings, CSV and restore controls are available for UI integration after approval. The numerical gates, real Firebase integration, physical experiments and continuous operating budget remain unvalidated in deployment.
